# Acceptance Gateway threat model

## Assets and assumptions

Assets are tenant isolation, bearer bindings, durable job integrity, existing acceptance authority, synthetic case/effect lineage, structured traces, and reproducible evidence. HTTP input, tokens, retrieved text, model output, worker status, timing, and transport outcomes are untrusted. The default route is localhost, synthetic, offline, and credential-free.

| Threat | Control | Residual risk / production gap |
|---|---|---|
| Authentication bypass | Every `/v1/*` route derives a tenant from a runtime bearer binding. Empty/malformed/unknown credentials fail closed. Bindings are held as SHA-256 digests and checked with constant-time comparison. | No TLS, rotation service, identity provider, revocation feed, or hardware-backed secret store is shipped. Binding beyond localhost would be unsafe. |
| Forwarded identity spoofing | Forwarded user/tenant headers are ignored; tenant comes only from authentication. | A production reverse proxy needs an explicit authenticated trust contract. |
| Tenant leakage by direct read | Job reads include authenticated tenant and job ID; foreign and absent objects return the same `404`. Public job shapes omit internal tenant IDs. | Timing side channels are not characterized. Production needs database policy enforcement and cache isolation. |
| Tenant leakage by list/cursor | Lists include tenant in the SQL predicate, use an exclusive cursor, and enforce a hard page limit. | Opaque cursors are encoded, not authenticated; they reveal no row data but production should sign cursors. |
| Cross-tenant idempotency probing | Uniqueness is `(tenant_id, idempotency_digest)`; equal foreign keys create independent jobs and expose no collision. Raw caller keys are not persisted. | High-volume probing is only constrained by the local in-memory rate limiter. |
| Replay/key substitution | The first canonical request digest is persisted. Exact replay returns the original; changed same-tenant payload conflicts. | Keys have no expiry policy in this lab, so storage grows until operator cleanup. |
| Queue claim race / duplicate execution | `BEGIN IMMEDIATE` atomically selects and updates one job. Completion requires the current random claim token. Concurrent tests and proof show one claim/execution per job, including processing beyond the original lease while renewal remains healthy. | SQLite is a single-host queue, not a distributed consensus system. A failure after an external side effect but before gateway completion can cause re-execution; only the shipped SQLite/idempotent-effect read-before-retry boundary is demonstrated. Catastrophic storage rollback is outside scope. |
| Stale or stolen lease | Lease duration is bounded to 1–300 seconds. A worker periodically renews only its current unexpired token and performs a final fenced renewal before completion. Expired abandoned jobs can be reclaimed with a new token; stale renewal/completion tokens fail, and expired claims stop at the configured attempt bound. | Renewal is best-effort on the same SQLite host. Scheduler stalls, process death, and storage failure can still lose a claim; live-provider exactly-once behavior is not claimed. |
| Unknown/lost effect response | The worker uses the existing bounded ledger path; the C12 synthetic case commits an effect, reports uncertainty, performs native read-before-retry, and proves one effect. | Real providers need provider-specific reconciliation and idempotency guarantees. |
| Stale generation | Existing ledger execution compares expected generation inside the transaction; gateway proof exercises rejection. Queue transport does not alter it. | Cross-database distributed generation control is not provided. |
| Approval or authority widening | API fields cannot express tenant, approval, amount, action, evidence, or authority. Worker calls the real Lab acceptance path; queue state never implies acceptance. | Adding richer job types would require a new threat review and strict versioned schema. |
| Prompt/retrieval injection | Retrieved content remains untrusted data and all existing proposal schema, citation, risk, evidence, materiality, approval, and action gates remain active. | Model influence and entailment remain residual risks described in `THREAT_MODEL.md`. |
| Synthetic provider/proposal timeout | Only the allowlisted `proposal_timeout` injected fault is accepted. It is classified and retried to a bounded terminal failure. | Live provider timeout semantics and billing are unexercised. |
| Database interruption | Readiness executes a SQLite probe and returns failure after interruption. Durable rows survive normal close/reopen. | Disk-full, corruption, backup restore, and multi-region recovery are outside scope. |
| Malformed or oversized input | Strict `application/json`, valid `Content-Length`, 16 KiB default cap, object type, exact fields, bounded identifiers, and stable errors. | Slow-client/socket exhaustion and reverse-proxy controls are not modeled. |
| Resource exhaustion | Per-tenant sliding-window request limit, request/page/lease/retry/load bounds, and separate workers. | Limiter state is process-local and resets on restart; production needs shared quotas, connection limits, deadlines, and admission control. |
| Log/token leakage | Request headers/bodies are never logged. Events use a one-way tenant-safe ID and recursive sensitive-key redaction. Tests scan event/evidence text for supplied secret values. | Key-name redaction is not a DLP system; production needs telemetry policy, retention, sampling, and sink controls. |
| Trace spoofing | W3C version-00 syntax, non-zero IDs, and request-ID character/length bounds are validated. The gateway generates spans itself. | Trace IDs are correlation, not identity or authorization. No OpenTelemetry exporter is shipped. |
| Evaluator overlap / proof gaming | Gateway controls are executable tests plus a deterministic outcome receipt. Load timings stay outside canonical identity. Existing held-out limitations remain disclosed. | Builder-side execution is `EXERCISED`, not independent verification. The synthetic corpus cannot establish external validity. |
| Schema rollback damage | Migration owns only `gateway_*` objects. Disposable proof reads a pre-existing lab row after rollback. | Future migrations can be data-bearing and will need version-specific forward/rollback fixtures and backup policy. |

## Fail-closed conditions

Unknown credentials, invalid traces, malformed JSON, oversized bodies, extra fields, invalid keys/cursors/limits, idempotency substitution, foreign reads, stale generations, missing approval, exhausted retries, stale completion tokens, unavailable SQLite, and unverifiable rollback all stop the requested transition. The implementation must stop rather than merge tenant storage, weaken atomic claims, bypass the Lab, or describe local measurements as production capacity.
